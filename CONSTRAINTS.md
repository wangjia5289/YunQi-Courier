# YunQi-Courier Engineering Constraints

These constraints define the integrated project. A change is complete only when it preserves them.

1. The repository root is the only build entry point. The root `pom.xml` owns the reactor and every module uses the `yunqi.courier` Java package and Maven group.
2. Dependency direction is one way: `common` -> `api` -> `kernel` -> `plugin`; `starter` is an application-only dependency aggregator. Common code must not depend on Netty or a concrete plugin.
3. Runtime extension points are loaded through `META-INF/yunqi-courier/plugin/<interface-name>`. Provider names are explicit and implementations must have a public no-argument constructor. The optional `weighted` load balancer interprets only the `weight`, `healthy` and `health` service attributes; malformed weights fall back to 1 and all unhealthy providers fail closed. The optional `least-active` balancer tracks calls locally through lifecycle callbacks.
4. Every network frame has a magic value, protocol version, message direction, serialization code, request id and a bounded payload. Decoders must reject malformed or oversized frames before allocation. Client-side pending requests are also bounded by configuration; overload must fail fast and release the slot on completion, timeout, channel failure or shutdown.
5. Request deadlines use a monotonic clock. Retry is opt-in (`retryable=true`), bounded, and rejected unless the reference declares `idempotent(true)` or the method carries `@CourierIdempotent`. Only transport/deadline and explicitly classified overload/unavailable responses are retried; serialized application errors are terminal.
6. Netty event-loop threads never execute user service methods. Business work runs on the bounded executor configured by `serverBusinessThreads` and `serverQueueCapacity`.
7. `start`, `stop` and `close` are idempotent. Stopping unregisters services, rejects new requests, broadcasts GoAway to accepted Netty channels, fails pending calls, drains bounded business work, and releases all event-loop and registry resources. Active server channels are bounded by `maxConnections`. A stopped bootstrap can be started again; references created before restart must be recreated.
8. Public service methods are the export boundary. The server validates the request id, service key, method signature, argument count and serializer code before dispatch. It also bounds request parameter metadata and attachment count/string sizes before reflection or business-queue submission.
8a. Annotation support is explicit only: `exportAnnotated` and `injectReferences` operate on the supplied object and never scan the classpath or mutate static/final fields.
9. JSON polymorphic deserialization is restricted to approved framework/JDK namespaces. New application DTO namespaces must be explicitly reviewed before being added to the allowlist.
10. Tests must run from a clean checkout with `mvn clean verify`. The default end-to-end path, primitive arguments, malformed frames, retry/deadline behavior, resilience controls and lifecycle restart must remain covered.
11. TLS is opt-in and transport-scoped. When enabled, Netty must use JDK key/trust stores and certificate-chain validation; trust-all managers are forbidden. `tlsMutualAuth` requires client certificates, hostname verification is enabled by default, and handshake failures must close the channel and fail pending calls. ZooKeeper TLS is configured independently through `registryTls*`, with hostname verification enabled by default. `reloadTlsContext()` refreshes material for new connections; OCSP/CRL and external key management remain deployment integrations.

11a. Optional payload transforms run after serialization and before framing. The fixed order is compression then authenticated encryption on encode, and decryption then decompression on decode. Transform configuration must match on both peers; decompression is bounded by `maxFrameLength`, and AES-GCM keys are supplied as Base64 16/24/32-byte material. TLS remains the preferred transport boundary.

12. Authentication is disabled by default. Configured bearer tokens require TLS and are checked before queue submission; authorization rules and the `RequestAccessController` SPI enforce service/method access. mTLS certificate sessions are exposed to custom controllers.
13. `ServiceRegistry` implementations must support lease renewal, watch cleanup and health updates where available. The memory registry is JVM-local; the file registry is lock-coordinated single-host discovery. Distributed registries remain replaceable plugins; the included ZooKeeper implementation uses ephemeral nodes and Curator watches.
13a. Bind and advertised endpoints are separate. A wildcard bind address must not be registered as a consumer endpoint; configure `advertisedHost`/`advertisedPort` for the routable address.
14. `referAsync` is an explicit asynchronous facade with cancellation. The current `Flow.Publisher` adapter is application-level; wire-level streaming requires a new protocol version and must preserve frame bounds/backpressure.
15. Metrics exporters/listeners must be non-blocking and isolated from invocation failures; production deployments can bridge snapshots to Micrometer/OpenTelemetry.
